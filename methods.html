How We Built This Site

Free AI Explorer lists 1,641 tools, lessons, and unplugged activities for K-12 computing, AI, and robotics. It favors tools that keep student data local. It is an AI-assisted experiment by Jeremy Riel, PhD, of the UIC TRAILblazer Lab. This page explains how we made it. The first part is for teachers. The expandable sections at the end are for researchers and IT staff.

The short version

This site is a focused collection. It does not inventory every AI tool for education. It gives priority to open-access tools and tools that run locally or on school servers. Cloud tools appear too, with clear privacy labels.

  • We built the site in three stages. First, we searched for tools and wrote a fact sheet for each one. Next, we sorted every tool with a fixed set of labels. Last, we wrote a plain-language page for each tool.
  • AI agents did most of the work. They searched the web, read websites, filled in fact sheets, and wrote pages. Small Python programs checked every step. A stage ended only after its checks passed.
  • Each fact sheet had to cite its sources. The search turned up 2,014 possible items. We kept 1,641 for the site.
  • We tested our labels for consistency. A second AI scored a random sample on its own. Then we compared the two sets of scores. Two labels fell short of our target. We tightened the scoring rules and scored every tool again.
  • We also fact-checked the pages. A reviewer compared 40 random pages with their fact sheets. It found 2 serious errors and 24 minor ones. We then rechecked the privacy text on every page. A new sample of 40 pages had no serious errors and 21 minor ones. We fixed all of them.
  • The privacy label tells you where student data goes. Each tool gets one of six labels. They are explained in the next section.
  • The labels lean toward caution on purpose. A missing fact gives an Unverified label. It never gives a safe-sounding one.
  • The site has limits. We did not test any tool in a classroom. We did not measure learning. AI wrote the pages, and AI makes mistakes. Prices and privacy terms change often. Check with the provider before you use a tool with students.
  • Please tell us about errors. You can reach the lab through trailblazerlab.org.

What the labels mean

Some labels come from fixed rules. A Python program reads each fact sheet and applies the same rule every time. We call these rule-based facts. Other labels are estimates. An AI agent scored them with a point system called a rubric. Two careful people could score these differently. Treat them as a starting point.

Privacy level

  • Stays on the device. The tool runs on the computer, tablet, or robot. Student work stays there.
  • Stays on a school server. The school runs the tool on a server it controls.
  • Local with optional cloud or accounts. The main features run locally. Accounts or some extras use a company's servers.
  • Sends student data to a company. Student work or account details go to an outside company.
  • No device needed. The activity uses paper, cards, or movement.
  • Unverified. The research could not confirm where data goes. Check before class.

On the site today, 474 items stay on the device and 33 stay on a school server. Another 223 are local with optional cloud or accounts. 261 send student data to a company. 128 need no device. 522 are unverified.

The other labels

  • Internet need. A tool that works only over the school network counts as offline. Unknown becomes Unverified.
  • Youngest users. The values are any age, 13 and up, 16 and up, 18 and up, or unknown. Any age means the research found no age limit. It also means the tool needs no account and keeps data local. Most items are unknown.
  • Ease for students. The score adds points for five things. These are the interface, the reading load, the time to a first success, any building of hardware, and how abstract the ideas are.
  • Teacher learning curve. This uses the same five points plus setup effort. Strong ready-made lessons lower the score.
  • Setup time. This counts prep time after the school has the item. It leaves out buying and shipping.
  • AI beginner. A yes means the tool teaches or uses AI in a visible way. It is also easy or moderate for students. It sets up in an hour or less. It shows students what the AI did.
  • Popularity. This blends six signals, such as how often other items name the tool. It counts no real users. It is an inferred index.
  • Classroom evidence. The values are peer-reviewed publication, documented classroom use, vendor examples only, or undocumented. Most peer-reviewed papers are design papers or small pilots. The label makes no claim about learning gains.

Limits you should know

  • English and Spanish only. We kept materials in these two languages. Good tools in other languages are missing.
  • The search stopped early. We searched in four rounds. Our rule said to stop once a round found under 5% new items. The last round still found 6.8% new items. The project lead closed the search anyway. Some tools are surely missing.
  • This is a snapshot. The data show what we found in November 2026. Tools change, close, or change their terms.
  • AI wrote the content. AI agents wrote the fact sheets and the pages. Our fact-checks found errors. Some errors surely remain.
  • No classroom testing. Nobody tried these tools with students for this project.
  • No learning impact. We did not measure whether any tool helps students learn.
  • Popularity is inferred. A formula estimates it from indirect signals. It does not count real users.
  • Some facts came from search snippets. A snippet is the short text in a search result. Some vendor sites blocked our agents. The fact sheets mark snippet-only facts. Pages may still state them plainly.
  • Subject tags are less certain. Our two AI scorers agreed less on subjects than our target. Each page shows the reason for each subject tag.
  • Estimates can read like facts. Pages describe ease and setup in plain sentences. These are rubric estimates.
Advanced technical methods: pipeline, discovery, dossiers, and rule labels (select to expand)

Pipeline architecture

The pipeline is manifest driven. A Python script defines the expected set of work items before any agent runs. Agents fill those items in batches. A validator then checks that every item exists and every value is allowed. A stage closes only after its validator passes.

Every stage can be re-run. Batch trackers record each batch as queued, running, or done. Interrupted batches go back to queued and run again. Raw outputs from a closed discovery round stay unchanged. All allowed label values live in one vocabulary file. Every later stage reads that file.

The stages run in this order.

  1. A query matrix expands into a list of planned queries with stable IDs.
  2. Sweep agents run the queries. They write raw candidate files and query logs for each round.
  3. A merge script deduplicates candidates and computes the new-item rate.
  4. Triage agents decide inclusion. A script checks coverage and writes the dossier manifest.
  5. Dossier agents write one fact sheet per included item. A dossier validator checks each one.
  6. A rule script assigns fact-based labels. Rubric agents score judgment labels. A validator checks values and computes agreement.
  7. Content agents write one page per item. A content validator and a style linter check each page.
  8. A build script renders the static site and a JSON index.

Models used

All agents were Claude Code subagents. Python created every batch and validated every output. The project lead assigned a model to each stage. The written log records only some of these choices. The list below comes from the lead's run records.

  • Triage first pass: Claude Haiku.
  • Triage review pass: Claude Sonnet.
  • First rubric pass: Claude Sonnet.
  • Second coder for the agreement sample: Claude Haiku.

Discovery design

The search space had 21 groups across five domains. Six groups covered AI. Seven covered computing. Four covered robotics. Two covered unplugged work. Two covered lessons and research literature. Each group had a focus statement, seed items, and 15 planned queries. The matrix held 315 planned queries in all.

Each Round 1 agent ran every planned query for its group. It also added at least 10 queries of its own. Agents paired subdomain terms with modifiers. Examples are offline, open source, runs locally, no account, K-12 classroom, lesson plan, and privacy. Agents logged every query and every candidate in a fixed CSV format. Each agent also wrote a landscape report with a gaps section.

Deduplication

Two rows merged once their loose name keys matched. The loose key drops case, punctuation, and generic words such as kit or software. It keeps text inside parentheses. An early version dropped that text. That version wrongly merged the Northwestern and Georgia Tech AI Unplugged sets. The fix kept them apart.

Rows that shared a URL under different names went to a review list. The script never merged those on its own. This kept separate products from one vendor apart. A review agent judged each flagged pair as merge, keep, or unsure. Confirmed merges went into a human-maintained alias file. That file holds 92 merges. Alias chains resolve to the final name.

Triage and inclusion rules

A triage pass sat between discovery and dossiers. It reviewed every candidate marked yes or maybe. An item was included only under all five of these rules.

  1. It is a distinct resource a teacher could pick up. Software, hardware, kits, platforms, curricula, lessons, activity sets, and AI models all qualify.
  2. K-12 students can use it. A teacher-only tool qualifies only for direct support of student-facing computing or AI work.
  3. It exists and can be obtained now.
  4. Its materials are available in English or Spanish.
  5. It fits computing, AI, robotics, or unplugged computing and AI instruction.

Triage did not judge privacy. Cloud tools stayed in with an honest data-flow rating later.

Haiku ran the first pass over 20 batches. A Sonnet review pass found that first pass inconsistent across agents. The review applied clarified rules. Content-only apps and general office tools were excluded. Tools with a built-in AI feature for students stayed in. Teacher-only AI assistants were excluded. Lesson and project libraries counted as curricula. PreK-only items were excluded. Legacy products with ongoing vendor support stayed in. The project lead then overrode a few calls. Kolibri, Internet-in-a-Box, and spreadsheets came back in.

Dossier schema

Each included item got a dossier. A dossier is a YAML fact sheet with short notes. Its fields cover the item type, domains, description, key features, AI functions, and where AI runs. A data-flow block records where the tool runs, account needs, internet needs, student data collected, and its destination. Other fields cover license, cost, platforms, setup steps, interface, grade claims, languages, classroom uses, lessons, evidence, popularity signals, maintenance, sources, and confidence.

Full dossiers required the official site, the docs, and the privacy policy for any software or connected device. They also needed one independent source from a web search. Light dossiers required the official page and at least one real lesson page. Agents could then name the tools, devices, and accounts each lesson needs. Light dossiers skip hardware, repository, and maintenance fields. They add duration and standards.

Honesty rules

  • Sources may list only pages the agent fetched and read.
  • A fact seen only in a search snippet carries a snippet tag in its source note.
  • Enum fields never take a guess. Unknown facts stay "unknown." Doubts go into open questions.
  • Classroom uses list documented uses only. Capabilities never count as uses.
  • A failed fetch counts as no evidence.

The THIN rule

The validator flags a dossier as THIN with fewer than 2 distinct source URLs. Agents were told never to repeat a URL to pass. A THIN result is an accepted, honest outcome. THIN items stay in the inventory with a limited information label.

Follow-up pass

The first validation found 1,612 valid dossiers and 104 THIN ones. A script then built a follow-up list. A targeted pass covered 197 items. Flags included widely used items with weak evidence, THIN items, low-confidence popular items, and items with values copied from discovery notes. Agents had up to 4 web searches per item. They also tried archives, help centers, app stores, and the student data privacy agreement registry. They had to verify copied values or reset them to unknown. After the pass, THIN dossiers fell from 104 to 19. The final validator reports 1,697 valid dossiers, 19 THIN, and none missing. A script also filled Wikipedia links. Early lookups had failed for lack of a User-Agent header.

Rule-based classification

A rule script reads only the dossiers. A missing or unknown input never produces a confident value. It produces Unverified or Unknown. This design biases the privacy labels toward caution.

Privacy level

The rules run in order. The first match wins. Site names appear first, then the internal code.

  1. No device needed, or paper. The tool runs on paper only, and the data destination is none.
  2. Unverified. The data destination is unknown or blank. A dossier note saying values came from discovery notes also triggers it.
  3. Sends student data to a company, or red. The destination is the vendor or a third party. AI running in the vendor cloud also triggers it.
  4. Stays on a school server, or blue. The destination is a school server.
  5. Local with optional cloud or accounts, or yellow. The destination is mixed. An optional or required account also triggers it.
  6. Stays on the device, or green. The destination is the device or none, and no account is needed.
  7. Anything left over is Unverified.

A product whose only cloud path is an optional add-on keeps its local rating. Its page names the add-on and tells the teacher how to leave it off. The privacy pass could later move a label toward caution. That step is described in the next section.

Other rules

  • Internet need maps the dossier field directly. Unknown becomes Unverified. A tool reached only on the school network counts as offline.
  • Youngest users runs a pattern search over the privacy notes, description, open questions, and accessibility notes. Patterns for 18, 16, and 13 run in that order. The highest match wins. A 13 match is skipped next to parental consent, junior account, or teacher-created account language. Any age requires no account and a known run location. Data must also stay on the device or go nowhere. All else is Unknown.
  • Cost reads the price fields and cost notes. Free needs zero prices or a free note with no paid terms. Subscription or per-seat language gives Paid license. Other items use bands on the lowest typical price, under $50, $50 to $200, or over $200. No price gives Unknown.
  • Open source, resource type, and platforms map dossier fields. Partial open source counts as open-source software.
  • AI capability uses keyword groups over the AI functions and model fields. Examples are chat for text, diffusion for images, and pose for vision.
  • Status reads the maintenance field, a status override file, and a legacy file. Discontinued items without legacy support leave the site.
  • Classroom evidence picks the strongest of four levels. A peer-reviewed entry gives the top level. A case study or a sourced classroom use gives documented use. Listed lessons alone give vendor examples. All else is undocumented.
  • Evidence confidence is limited for fewer than 2 distinct sources or low agent confidence. High confidence gives well documented. All else is partly documented.

Popularity formula

Popularity is a fixed formula. Each part is scaled from 0 to 1 by dividing by its maximum across all 1,716 classified items. The weights sum to 1.

PartScalingWeight
Mentions by other items in the inventorylog of 1 plus count0.30
GitHub starslog of 1 plus stars0.20
Discovery countraw count0.15
Wikipedia article exists1 or 00.15
Documented classroom usesraw count0.10
Query groups that found the itemraw count0.10

The protocol names the last part curated-list mentions. The script approximates it with the number of discovery groups that found the item. Discovery count carries less weight by design. Later rounds skipped items already found. The count therefore undercounts famous tools. Live search ranking changes daily. The formula leaves it out for that reason.

Mentions count how many other dossiers name the item. The match is case sensitive and needs a whole phrase. It uses the display name without parenthetical text, plus the item's aliases. Names under 4 characters are skipped. A list of common words is skipped too. Lowercase single-word aliases are skipped. Aliases that equal another item's name are skipped too. Each other dossier counts once. Lessons and kits name the tools they use. Classroom staples such as Scratch and micro:bit rank high as a result.

Related products

Each on-site item lists up to 6 related items. The score for a pair has three parts, each scaled from 0 to 1.

PartMethodWeight
Tag overlapWeighted Jaccard over six label sets0.45
Text similarityTF-IDF cosine over name, description, and key features0.40
Companion bonus1 for a dossier naming the other item, else 00.15

The tag weights are subjects 3, tech type 2, AI capability 2, grade band 1, learning purpose 1, and resource type 1. The No AI capability value is ignored. For each set, the overlap is the shared values over the union. The weighted sum is divided by the total weight of sets with any values.

Text vectors use word counts with sublinear term weights. Each word gets 1 plus the log of its count, times the log of the inverse document frequency. Common stop words are dropped. Words found in 30% or more of items are dropped. Companion links use a whole-name match of 5 or more characters, in either direction. Ties break on popularity, then on the item ID. The script uses no randomness and no network.

Advanced technical methods: rubric scoring and agreement statistics (select to expand)

Rubric classification

Agents scored the judgment labels in 83 batches of about 20 items. They used only the batch extract and the dossier. They had no web access. Each score had to cite the dossier field or phrase behind it. A validator checked every value. It also checked that each band matched its point total.

Student ease

Five factors each score 0, 1, or 2. A total of 0 to 2 is easy. A total of 3 to 5 is moderate. A total of 6 or more is advanced.

Other rubric labels

  • Teacher learning curve uses the same five factors plus a setup factor from 0 to 2. Strong lesson materials subtract 1. The same bands apply.
  • AI beginner is yes under four conditions. The tool teaches or visibly uses AI. Student ease is easy or moderate. Setup takes minutes or about an hour. The tool gives clear feedback on what the AI did. Tools with no AI are always no.
  • IT involvement has four levels. None covers paper and web tools with no install or account. Teacher can install covers app store apps, teacher-account web tools, and plug-in hardware. IT installs it covers managed desktop installs, firmware flashing, and district agreements. Needs a server admin covers self-hosted servers and multi-user model runtimes.
  • Setup time counts work after the item is in hand. Minutes means a class could start the same day. About an hour means one prep session, such as installs, accounts, charging, or class-set flashing. A day or more means kit builds, lab-wide toolchain imaging, servers, or district identity integration.
  • Subjects take 1 to 5 of 14 school subjects. Each needs a one-sentence reason. Computer science is assigned only for coding, computing, or study of how computers or AI work.
  • Grade bands start from the claimed range and documented uses. A band is added only for a fit in reading load and ease.
  • Learning purpose marks learning about AI and computing, using them in another subject, or both.

Double-coding sample

A script drew a fixed-seed 10% random sample. The seed was 20261119. The sample held 160 items. A second model scored them on its own from the same extracts. Agreement used three statistics.

  • Cohen's kappa for nominal labels.
  • Quadratic weighted kappa for the ordered three-band labels.
  • Mean per-value Cohen's kappa for the multi-value sets. Each value is treated as a yes or no call.

The target was 0.7. A lower value triggered a rubric revision and a re-run.

Adjudication

An adjudicator reviewed 75 items where the two coders disagreed on student ease or setup time. It made a final call on each. Steps caused the most factor splits, at 35. Interface followed at 31, abstract at 25, reading at 15, and assembly at 11. Setup splits were 29 between minutes and hour and 20 between hour and days. The band itself differed on 39 items.

The adjudicator found four main causes. One coder scored complex GUIs higher on interface. The coders blurred first success, unit length, and teacher setup. They split on whether student or admin work counts. They also split on blocks programming as abstract or concrete.

Anchor revision

The adjudicator wrote sharper anchors from these cases. Four general rules lead the anchor file.

  1. Score only the student's experience. Teacher and IT work count only in setup time and the teacher rubric.
  2. For mixed items, score the mode the resource's own lessons use. Pick the lowest programming mode that beginners can use.
  3. Score the default path in the dossier. Optional extras never raise a score.
  4. Infer an unknown field from the named platform.

Factor anchors followed. Any GUI scores 0 on interface, however complex. First success means the first visible working result. A long unit alone never sets steps to 2. Setup time excludes purchase, shipping, and license approval. Each level lists worked examples from the adjudicated items.

Re-score

All items were re-scored for student ease and setup time. Sonnet agents ran 42 batches of about 40 items with the new anchors. The validator then reported 0 problems. The project lead made consistency fixes afterward. Pip-only or conda-only installs across a lab became a day or more. Twine and similar link-based story tools became interface 1 and abstract 0. These rules were added to the anchor file.

Early first-pass batches had counted purchase time as setup. That error could push hardware toward a day or more. It could also wrongly set AI beginner to no. A targeted recheck covered those hardware items. A separate review covered AI beginner calls.

Advanced technical methods: pages, quality checks, and site (select to expand)

Content generation

Content agents wrote one page per item. They used only the batch extract and the dossier. They had no web access. The brief banned invented features, prices, studies, ages, and standards. Unknown facts stay unknown.

Each page has eight sections in a fixed order. These are the overview, benefits for students, teachers, and schools, a getting-started checklist, the AI section, privacy and safety, and ideas by subject. The checklist has 5 to 8 steps. It must include any security step the dossier supports. Examples are changing a default password and turning off telemetry. Each tagged subject gets exactly 5 activity ideas. The writing level targets about grade 8.

Agents wrote 110 batches of 15 items. The content validator checks the front matter and section order. It also checks bullet and checklist counts, one subject section per tag, five ideas each, no extra subjects, no URLs in prose, and a minimum length. It runs the style linter and allows 0 errors. The linter flags dashes, semicolons, banned subordinate openers, negative parallelism, bold lead-ins, and stock lead-ins. It warns on hype words, parenthetical asides, and long or multi-clause sentences. All 1,641 pages pass with 0 problems.

Privacy pass

The first fact-check found dropped privacy caveats. The cause was the page writers' input. They saw only a summary of each dossier. A privacy pass then re-checked all 1,641 pages against the full dossiers.

Agents fixed five kinds of problems.

  • A claim more reassuring than the dossier supports.
  • A missing caveat from the data flow, open questions, or notes.
  • COPPA language misread as an age limit.
  • Unverified facts stated as fact.
  • An understated claim, such as a signed privacy agreement left out.

Agents rewrote each privacy section as 3 to 5 sentences. They also flagged labels that looked wrong. A script applied every flag that moved a label toward caution. The order of caution for privacy runs from paper and device, to school server, to optional cloud, to unverified, to company. Internet need runs from offline, to setup only, to always or unverified. Age runs from any, to unknown, to 13, 16, and 18. Flags toward less caution went to the project lead. The pass applied 240 cautious labels automatically. The lead decided 12 more.

Minimum-age audit

The first age rule read "under 13" COPPA language as an age floor. That language is a data rule. Many such products are built for children. The rule was fixed to skip 13 next to parental consent language. Agents then audited 103 items. They read every dossier sentence that mentions an age. Their calls went into an age override file. The rule script applies that file.

Its speech feature uses a cloud service during use. Minor issues included dropped caveats and overclaimed AI links. All 47 issue rows were fixed or already resolved.

Both reports also listed rubric judgments stated as facts. Examples are "easy to learn" and "setup takes days." These match the classification and were not counted as errors. A reader still cannot tell they are estimates.

These checks have limits. They covered 80 of 1,641 pages. They tested pages against dossiers only. Nobody re-checked the dossiers against the live web.

Link checking

A link checker tested every outbound URL the site shows. These include official URLs, more-info links, and sources. Each URL got a GET request with redirects, reading the first 200 KB. The checker assigned four flags.

  • Dead means HTTP 404 or 410, a DNS failure, or a refused connection.
  • Error means other HTTP errors or timeouts. Most were bot blocking.
  • Moved host means the final host differs from the original beyond www or https.
  • Parked means page text looks like a parked, for-sale, gambling, or adult domain.

Image sourcing

The protocol put openly licensed images first. A script searched Wikimedia Commons for each item. Its match rate was low. A second script tried Wikipedia lead images. Wikimedia throttled the downloads and stopped it. The project lead chose to launch with local category icons. The site shows icons for that reason. The photo script can run again later.

Site construction

The site is a static folder with no database. A build script renders every page from Markdown sources. It also writes a JSON index for the explorer. The build produces 1,648 pages: 1,641 tool pages and 7 other pages. The site can be embedded in WordPress through a shortcode plugin. It is hosted on GitHub Pages.

The site makes no third-party requests. Scripts, styles, and icons all load from the site itself. It has no ads, trackers, or analytics. My List lives only in the visitor's browser. Each page sets this Content Security Policy.

  • default-src 'self'
  • img-src 'self' data:
  • style-src 'self'
  • script-src 'self'
  • object-src 'none'
  • base-uri 'self'
  • form-action 'none'
  • connect-src 'self'

The server config adds frame-ancestors. It allows framing only by the site itself and trailblazerlab.org.

An accessibility script checks every page. It tests each text and background color pair in light and dark modes against WCAG AA contrast of 4.5 to 1. It checks for a lang attribute, one h1, a main landmark, and a skip link. It also checks heading order, image alt text, form labels, unique IDs, and button names. The final build had 0 problems. Reflow passed at 320 and 768 pixels. My List, share links, and the WordPress embed were tested in Chrome.

Reproducibility

The pipeline lives in a private workspace. Only the built site is public. Researchers who want the pipeline files can ask through trailblazerlab.org. The workspace holds these parts.

  • A research protocol, a taxonomy, a style guide, and a runbook.
  • The agent briefs for every stage and round.
  • Config files for the query matrix, dossier schema, label vocabulary, and aliases.
  • Override files for status, legacy products, site exclusions, labels, minimum ages, and blocked links.
  • Raw round outputs, query logs, the candidate list, triage decisions, and every dossier.
  • Rubric outputs, double-code outputs, adjudication calls, and re-score outputs.
  • Reports on saturation, triage, dossier validation, agreement, fact-checks, links, and gaps.

The scripts form a chain. A query builder expands the matrix. A merge script deduplicates and computes saturation. A triage checker writes the dossier manifest. A dossier validator and a follow-up selector come next. The rule script assigns labels and popularity. Helper scripts count mentions and look up Wikipedia articles. A batch maker draws the fixed-seed sample. A rubric validator computes agreement. A content batch maker, a content validator, and the style linter check pages. A flag script applies cautious labels. Further scripts compute related items, check links, check accessibility, and build the site.

The rule, mention, and related-item scripts are deterministic. The double-code sample uses a fixed seed. The agent stages are not deterministic. Web search results also vary by date and engine. A re-run will find a somewhat different set of items. The protocol describes a re-run. Archive the research folder with a date. Edit the query matrix and raise its version. Then follow the runbook from the top. The merge script compares the new list with the archive and reports retired and new items.
